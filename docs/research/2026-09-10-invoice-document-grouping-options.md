# 거래명세표 품목 묶음 발행 수정안 조사

## 질문

품목마스터에서 대표 품목 합산을 설정하지 않은 서로 다른 품목을 같은 거래명세표에 출력할 수 있어야 하는가? 가능하게 한다면 문서 분리 기준을 어디에 둘 것인가?

## 현재 구현의 근거

- 문서 그룹 키는 `siteId + contractCategoryId + itemId`다. 따라서 실제 품목 ID가 다르면 문서가 분리된다. [calculation.ts:54-64](../../src/lib/invoices/calculation.ts#L54-L64)
- `invoiceDisplayItemId`를 이용한 합산은 이미 만들어진 문서 안의 출력 행을 합치는 단계다. 대표 출력 품목 설정만으로 문서 경계는 바뀌지 않는다. [calculation.ts:108-118](../../src/lib/invoices/calculation.ts#L108-L118)
- 발행 후보도 계약 구분 안에서 실제 `itemId`별로 생성된다. [service.ts:112-195](../../src/lib/invoices/service.ts#L112-L195)
- 신규 발행 요청은 하나의 `issueItemId`만 대상으로 삼는다. [schemas.ts:22-31](../../src/lib/invoices/schemas.ts#L22-L31)
- 발행 snapshot도 현재는 단일 `issueItemId`와 `issueItemName`을 보존한다. [schema.prisma:496-501](../../prisma/schema.prisma#L496-L501)

따라서 현재 `AGGREGATED`는 "서로 다른 품목을 한 문서로 묶기"가 아니라 "한 품목 문서 내부의 출력 행 합산"이다.

## 공통 제약

거래명세표에는 문서 단위의 발행일이 하나만 있으므로, 품목별 발행일이 다르면 같은 문서로 합칠 수 없다. 모든 안은 최종 그룹 키에 `issueDate`를 포함하거나, 묶을 품목의 발행일을 같게 맞추도록 해야 한다.

## 수정안 1: 계약 구분별 발행 모드 추가

### 방식

발행 화면에 두 모드를 둔다.

- `품목별 발행`: 현재 동작. `현장 + 계약 구분 + 품목 + 발행일` 기준
- `계약 구분별 발행`: 같은 현장·계약 구분·발행일의 품목을 한 문서로 묶고, 인쇄 본문에는 품목별 행을 출력

대표 출력 품목 설정은 두 모드 모두 문서 내부 행 합산에만 사용한다. 계약 구분별 모드에서는 여러 품목이 들어가므로 발행 snapshot은 `issueItemId = null`, `issueItemName = 여러 품목`으로 저장하고, 문서와 원장 link로 실제 품목을 추적한다.

### 장점

- 기존 품목별 발행을 보존하면서 사용자가 업무 상황에 따라 선택할 수 있다.
- 기존 품목마스터 데이터 구조를 재사용한다.
- 현재 요구인 "합산 설정이 없는 품목도 한 문서"를 가장 직접적으로 해결한다.

### 주의점

- 일부 품목만 먼저 발행하면 계약 구분별 묶음의 잔여 원장을 다시 후보로 계산해야 한다.
- 선택 품목의 발행일이 다르면 자동으로 문서를 나누거나, 같은 문서 발행을 막고 날짜를 맞추도록 해야 한다.
- 대체 발행은 기존 활성 문서의 전체 원장 집합을 기준으로 해야 하며, 단순히 `issueItemId` 하나를 비교하면 안 된다.

### 적합한 경우

같은 계약 구분의 품목은 기본적으로 한 거래명세표로 보내고, 특정 상황에서만 품목별 분리가 필요한 경우.

## 수정안 2: 품목마스터에 별도 발행 그룹 마스터 추가

### 방식

대표 출력 품목과 별개로 `InvoiceIssueGroup`을 만든다. 품목은 선택적으로 발행 그룹에 연결한다. 문서 그룹 키는 다음과 같이 바꾼다.

`현장 + 계약 구분 + 발행 그룹 또는 실제 품목 + 발행일`

발행 그룹이 없는 품목은 현재처럼 단독 품목 문서가 된다. 발행 그룹이 같은 품목만 한 문서에 들어가며, 인쇄 행의 품목명과 합산 여부는 기존 대표 출력 품목 설정이 계속 담당한다.

### 장점

- 문서 묶음 규칙과 인쇄 표시 규칙을 분리할 수 있다.
- "안전 관련 품목은 한 장", "교육 관련 품목은 별도" 같은 반복 업무 규칙을 명시적으로 관리할 수 있다.
- 기본값을 그룹 미지정으로 두면 기존 발행 결과와 호환하기 쉽다.

### 주의점

- 품목마스터 또는 계약 구분별 관리 화면과 migration이 필요하다.
- 품목이 계약 구분에 따라 다른 발행 그룹에 속해야 한다면 단순히 Item에 그룹 ID 하나를 두지 말고 계약 구분-품목 매핑 모델을 검토해야 한다.
- 발행 snapshot에 그룹 ID와 그룹명을 고정해야 이후 마스터 변경이 과거 문서에 영향을 주지 않는다.

### 적합한 경우

같은 묶음 규칙을 매월 반복하고, 담당자가 발행 화면에서 매번 임시로 품목을 선택하지 않기를 원하는 경우.

## 수정안 3: 발행 시 임시 다중 품목 묶기

### 방식

현재 품목별 후보 행은 유지한다. 사용자가 여러 행을 선택한 뒤 `같은 거래명세표로 묶기`를 실행하면, 선택 행을 하나의 발행 target으로 변환한다. 동일한 발행일을 가진 선택 행만 묶고, 날짜가 다르면 미리보기에서 문서를 자동 분리한다.

서버 target은 단일 `issueItemId` 대신 `issueItemIds` 또는 검증된 `revenueEntryIds` 집합을 받는다. 문서 snapshot은 단일 품목 대신 `여러 품목`으로 저장하고 원장 link를 기준으로 실제 구성 품목을 확인한다.

### 장점

- 마스터 변경 없이 특정 발행 건만 유연하게 처리할 수 있다.
- 예외적인 고객 요청이나 일회성 묶음 발행에 적합하다.
- 기존 품목별 후보 조회와 발행일 편집 UI를 최대한 유지할 수 있다.

### 주의점

- 같은 묶음을 매번 수동으로 선택해야 한다.
- 중복 선택, 일부 발행, 재시도, 동시 발행 검증이 복잡해진다.
- 계약 구분이 다른 행을 묶을 수 없게 해야 하며, 묶음 결과의 대표 문서명과 이력 검색 기준을 새로 정해야 한다.

### 적합한 경우

묶음 규칙이 정해져 있지 않고, 소수의 예외 발행만 처리하면 되는 경우.

## 권장 순서

1. **단기 권장: 수정안 1**
   계약 구분별 발행 모드를 추가한다. 현재 요구사항을 가장 적은 마스터 변경으로 해결하고, 기존 품목별 발행도 유지할 수 있다.
2. **반복 업무가 확인되면: 수정안 2**
   매월 같은 품목 조합을 묶는다면 발행 그룹 마스터로 승격한다. 이때 대표 출력 품목과 발행 그룹을 별도 개념으로 유지한다.
3. **예외 처리용: 수정안 3**
   정형화되지 않은 일회성 고객 요청만 임시 묶기로 처리한다. 기본 발행 정책으로 채택하면 검증과 이력 관리 비용이 커진다.

## 구현 전 확정해야 할 질문

1. 같은 현장·계약 구분에서 발행일이 같은 품목은 기본적으로 항상 한 문서여야 하는가?
2. 품목별 발행일이 다르면 자동으로 여러 문서로 나누면 되는가, 아니면 사용자가 날짜를 같게 맞춰야 하는가?
3. 한 문서 안에서는 서로 다른 품목을 원장 건별 행으로 표시할 것인가, 대표 출력 품목 설정이 있는 경우에만 행 합산할 것인가?
4. 일부 품목을 먼저 발행한 뒤 남은 품목은 같은 문서의 추가 발행본으로 만들 것인가, 아니면 기존 문서를 대체 발행해야 하는가?

## 후속 검토: 자동 그룹 표시와 사용자 지정 분리

### 결론

가능하다. 가장 자연스러운 방식은 발행일 선택 화면에서 먼저 **자동 그룹**을 계산해 보여주고, 사용자가 같은 자동 그룹 안에서만 **문서 분리**를 추가하는 방식이다.

자동 그룹의 기본 키는 다음과 같다.

`현장 + 계약 구분 + 발행일`

사용자가 분리한 뒤의 실제 발행 키는 다음과 같다.

`현장 + 계약 구분 + 발행일 + 사용자 문서 그룹`

발행일이 다른 행은 자동으로 다른 그룹이며, 사용자가 합칠 수 없게 한다. 계약 구분이 다른 행도 같은 방식으로 합칠 수 없게 한다.

### 화면 제안

현재처럼 품목별 후보 행을 유지하되, 행에 다음 정보를 추가한다.

- `자동 그룹`: 예를 들어 `강남 현장 / 스마트건설안전 / 2026-09-10`
- `그룹 품목 수`: 현재 그룹에 포함된 선택 가능 품목 수
- `그룹 공급가액`: 같은 자동 그룹의 미발행 금액
- `문서 분리`: 해당 행을 새 거래명세표 그룹으로 이동하는 명령

화면 상단에는 자동 그룹별 요약을 함께 표시한다.

```text
강남 현장 · 스마트건설안전 · 2026-09-10
  품목 A  400,000원
  품목 B  600,000원
  예상 거래명세표 1건
  [선택 품목을 별도 문서로 분리]
```

분리 명령을 실행하면 그룹이 `그룹 1`, `그룹 2`로 나뉘고, 각 행에서 현재 소속 그룹을 확인할 수 있어야 한다. 분리된 그룹을 다시 합치는 `그룹 합치기`도 제공하는 것이 안전하다.

### 발행 요청 모델

현재 신규 target은 단일 `issueItemId`를 받으므로, 여러 품목 그룹을 표현할 수 없다. 신규 target을 다음 형태로 확장해야 한다.

- `issueRevenueEntryIds` 또는 검증된 `issueItemIds`: 한 문서에 포함할 원장 범위
- `issueDate`: 해당 문서의 발행일
- `documentGroupKey`: 화면에서 만든 임시 그룹 식별자
- `candidateKeys`: 발행 결과를 화면의 품목 행과 다시 연결하기 위한 클라이언트 후보 키

실제 서버 검증은 `documentGroupKey`를 신뢰하지 않고, target의 원장 ID 집합이 다음 조건을 만족하는지 확인해야 한다.

- 모두 같은 마감 회차·현장·계약 구분에 속함
- 모두 현재 미발행 상태임
- 모두 동일한 `issueDate`를 사용함
- 미리보기 시점의 마감 version과 revenue fingerprint가 변하지 않음

### 저장 및 대체 발행

여러 품목이 포함된 문서는 기존 단일 `issueItemId`에 하나를 억지로 저장하지 않고 `issueItemId = null`, `issueItemName = 여러 품목`으로 보존한다. 실제 구성 품목은 기존 `InvoiceRevenueLink`와 snapshot fingerprint로 추적한다.

사용자 분리 그룹을 대체 발행에서도 유지하려면 `InvoiceDocument`에 발행 당시의 `documentGroupKey` 또는 별도 그룹 snapshot을 저장해야 한다. 저장하지 않으면 대체 발행 시 사용자가 만든 분리 경계를 복원할 수 없고, 모든 활성 원장이 다시 하나의 자동 그룹으로 합쳐질 수 있다.

### 권장 UX 정책

1. 기본 상태는 자동 그룹으로 표시한다.
2. 같은 자동 그룹 안에서만 수동 분리를 허용한다.
3. 발행일을 바꾸면 행을 새 자동 그룹으로 이동시키고, 기존 수동 분리 상태는 같은 자동 그룹 안에서만 유지한다.
4. 미리보기에는 `자동 그룹 수`와 `최종 거래명세표 수`를 모두 표시한다.
5. 발행 후에는 실제 생성된 거래명세표 번호와 그룹에 포함된 품목을 함께 보여준다.

### 권장안

이 요구에는 단순한 계약 구분별 일괄 발행보다 **자동 그룹 표시 + 동일 그룹 내 수동 분리**가 더 적합하다. 기본 업무는 자동화하면서도, 고객별 요청이나 내부 정산 사유로 같은 현장·계약 구분·발행일을 여러 장으로 나눌 수 있기 때문이다. 다만 수동 분리 경계를 대체 발행에서도 보존해야 하므로, `documentGroupKey` snapshot을 포함하는 것을 전제로 한다.
